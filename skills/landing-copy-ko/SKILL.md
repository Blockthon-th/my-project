# 한국어 랜딩 카피

만든 사람은 자기 제품을 설명하려 든다. 읽는 사람은 자기 문제를 확인하고 싶어 한다. 이 간극에서 대부분의 랜딩이 실패한다.

## 시작하기 전에 정할 것

1. **독자가 이 제품을 전혀 모른다고 가정한다.** 업계 사람도 아니라고 본다.
2. **첫 화면 금지어 목록을 먼저 만든다.** 자사 제품명, 의존하는 기술 스택 이름, 내부 용어, 업계 약어를 전부 적는다.
   이 목록은 나중에 기계로 검사한다. 사람 눈으로 판단하면 만든 사람은 늘 통과시킨다.
3. **파는 쪽인지 사는 쪽인지 한쪽을 정한다.** 양면 시장이어도 첫 화면은 한쪽에만 말을 건다.
   헤드라인이 한쪽을 향하는데 화면에는 반대쪽 물건이 깔려 있으면 5초 안에 헷갈린다.

## 첫 화면

제목 한 줄, 본문 두세 줄, 한 줄 강조, 버튼. 그게 전부다. 이미지도 카드도 숫자도 넣지 않는다.

- 제목은 **독자가 이미 겪은 상황**을 말한다. 제품이 무엇인지가 아니라.
- 본문에서 그 상황을 구체적인 장면으로 푼다. 추상명사 대신 실제로 일어나는 일을 쓴다.
- 한 줄 강조에서 이 제품이 그 상황에 뭘 하는지 말한다.
- 제품명·기술명은 스크롤을 내린 뒤에 처음 나온다.

나쁜 예와 좋은 예 (실제로 반려당한 문장과 고친 문장이다):

> ✗ 에이전트가 남긴 작업 과정을 다른 에이전트에게 팝니다.
> 사본이 아니라 기간제 접근권입니다. 값은 Sui 로 치르고 기록은 Walrus 에 두고 기간이 지나면 Seal 이 열쇠를 거둡니다.

첫 문장에 모르는 제품명이 셋이다. 읽는 사람은 한 문장도 해석하지 못한다.

> ✓ 당신의 시행착오를 사겠습니다.
> AI 랑 씨름하다 알게 된 것들 말이에요. 버튼이 안 보여서 고치고, 제목이 세 줄로 떨어져서 또 고치고.
> 다 고치고 나면 그 대화는 그냥 사라져요.

## 설명하지 말고 보여준다

줄글 소개 섹션은 읽는 사람에게 이해라는 숙제를 준다. 실제 결과물이나 팔고 있는 물건을 첫 화면 가까이 깔면 숙제가 사라진다.
자세한 설명은 상품 상세나 하위 페이지로 내린다.

판단 기준은 페이지 길이가 아니다. 첫 화면만 보고 "여기서 뭘 파는지" 를 한 문장으로 말할 수 있는지다.
누군가에게 5초만 보여주고 물어보라. 못 말하면 실패다.

## 말투

한국어 소비자 대상 랜딩은 **해요체**가 합니다체보다 가깝게 읽힌다. 하나로 통일한다.

문제 섹션은 3인칭 설명 대신 **독자가 했을 법한 말을 1인칭으로** 인용한다.

> 남들이 좋다는 거 다 써봤는데 안 맞아요
> 토너 먼저? 세럼 먼저? 검색할수록 더 헷갈려요

실제 대화 기록이 있으면 그걸 그대로 쓴다. 지어낸 문장보다 훨씬 잘 읽힌다.

## AI 가 쓴 한글 티

한국어 카피를 쓰고 나면 아래를 전수 검사한다. 하나라도 남으면 사람이 쓴 글로 안 읽힌다.

| 패턴 | 예 | 고치는 법 |
|---|---|---|
| 결산 관용구 | 결론적으로 · 따라서 · 이를 통해 · 정리하자면 | 문서 전체 1~2회 이하로 줄인다 |
| 의의 과장 | 시사하는 바가 크다 · 주목할 만하다 | 삭제하거나 구체적 결론으로 |
| 열거 도입 | 크게 세 가지로 나눌 수 있다 · 다음과 같은 | 도입구 없이 바로 본론 |
| 분열문 | 핵심은 ~다 · 필요한 것은 ~이다 · 문제는 ~다 | 주어와 서술을 직결한다 |
| 도치 결산 | ~하는 이유다 · ~로 이어진다 | 순방향 단언으로 |
| 대구 반복 | A 가 아니라 B · A 인가 B 인가 | 문서 전체에서 한 번만 |
| 변환 공식 | X 에서 Y 로 · 단순한 X 를 넘어 Y | 직접 단언으로 |
| 연결어미 뒤 쉼표 | ~하고, ~하며, ~지만, | 쉼표를 뺀다. 가장 흔한 티다 |
| 따옴표 강조 | 다섯 번 이상 | 진짜 인용만 남긴다 |
| 대시 부가설명 | 문장마다 — 로 덧붙이기 | 쉼표·괄호·별도 문장으로 |
| hype 어휘 | 혁신적 · 획기적 · 압도적 · 전례 없는 | 구체적 수치나 사실로 |

문장 길이를 고르게 만들지 않는다. 짧은 문장 사이에 긴 문장을 하나 섞는다.
같은 종결어미가 네 문장 연속 나오면 바꾼다.

## 레퍼런스 고르는 법

제품 카테고리가 같다는 이유로 고르면 실패한다. **독자가 이미 익숙한 맥락**으로 고른다.
개발자 도구 랜딩의 다크 테마와 코드 패널은 개발자에게만 읽힌다. 독자가 일반 사용자면 그 관습이 오히려 장벽이 된다.

레퍼런스를 정했으면 실측해서 쓴다. 브라우저 콘솔에서 배경색·글자색·폰트 스택·h1 크기와 자간·버튼 라운드를 뽑고,
섹션이 몇 개인지 문서 높이가 얼마인지 본다. 눈대중으로 따라 만들면 어중간해진다.

## 스크롤 연출

- **스크롤을 가로채지 않는다.** 페이지가 멋대로 멈추거나 튀면 독자가 떠난다.
- IntersectionObserver 로 화면에 들어올 때 나타나기만 하고, 다시 숨기지 않는다.
- `prefers-reduced-motion: reduce` 면 처음부터 전부 보이게 한다.
- 빠르게 스크롤했을 때 안 나타나고 남는 요소가 없는지 반드시 확인한다.
- 모바일에서는 한 화면에 하나씩만 나오면 너무 느리다. 두세 개를 같이 보인다.

## 정적 페이지가 외부 API 를 직접 읽는다면

설계하기 전에 CORS 부터 확인한다. 나중에 알면 구조를 다시 짜야 한다.

```bash
curl -s -i -X POST "<endpoint>" -H "Origin: https://example.com" -H "Content-Type: application/json" -d '<body>' | grep -i "^HTTP|access-control"
```

`access-control-allow-origin` 이 있어야 한다. 이미지는 헤더만으로 판단하지 말고 브라우저에서 `naturalWidth > 0` 까지 실제로 확인한다.
content-type 헤더가 없어도 대개 렌더되지만 `x-content-type-options: nosniff` 가 걸린 경우가 있다.

## 마무리 검사

`tools/check-copy.mjs` 를 돌린다. Playwright 가 필요하다.

```bash
node tools/check-copy.mjs <html 또는 url> --banned "제품명,기술명,내부용어"
```

경로는 저장소 루트 기준이다. Playwright 가 `tools/node_modules` 에만 있어서 이 폴더에 같이 둔 `check-copy.mjs` 사본을
그 자리에서 돌리면 `Cannot find package 'playwright'` 가 난다. 사본은 스킬을 다른 저장소로 옮길 때 쓰고
여기서는 `tools/` 쪽을 돌린다.

여섯 항목을 본다. 첫 화면 금지어 · 말투 일관성 · 분열문 · 대시 절제 · 따옴표 절제 · 375px 가로 스크롤.
형태소 분석기를 쓰지 않으므로 완벽하지 않다. 실패로 뜬 항목은 사람이 한 번 보라는 신호다.

그리고 반응형을 1440 · 768 · 375 세 폭에서 확인한다. 가로 스크롤이 있으면 다른 걸 아무리 잘해도 허술해 보인다.
