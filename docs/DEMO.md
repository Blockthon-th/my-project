# 데모 시나리오 (3분)

> 핵심 한 장면: **같은 질문에 대해, 구독 전 에이전트는 일반론을 말하고 구독 후 에이전트는 이전 소유자의 실제 삽질 기록으로 답한다.**

## 준비 (데모 전에 미리)

1. 판매자 팩을 채워둔다.
   ```powershell
   cd scripts
   npm run sync -- --dry     # 필터 결과 확인
   npm run sync              # 팩 생성 + 기억 업로드 + 미리보기 등록
   ```
2. 구독자 지갑에 가스가 있는지 확인 (`sui client faucet --address <구독자>`).
3. 구독자용 Claude Code 창을 하나 열고 `.mcp.json` 의 `memory-market` 서버가 붙었는지 확인.
4. 구독 상태를 초기화하려면 팩의 `ttl_ms` 를 짧게 두거나 새 구독자 주소를 쓴다.

## 진행

### 1. 문제 제기 (30초)
"Sui 는 개발자 온보딩이 어렵다. 문서와 예제가 최근 변경을 못 따라가서, 처음 붙이는 사람은 같은 함정에 똑같이 빠진다."
→ 우리가 2주간 실제로 빠진 함정 목록(`docs/dev-memories.md`)을 보여준다. **지어낸 게 아니라 이 프로젝트를 만들며 쌓인 것.**

### 2. 구독 전 (30초)
구독자 에이전트에게 묻는다:
> "Sui SDK 로 트랜잭션을 보내는데 `Session key has expired` 가 뜬다. 방금 세션 키를 만들었는데 왜지?"

→ 일반론("만료 시간을 늘려보라", "다시 만들어보라") 수준의 답.

### 3. 시장 확인 → 구독 (45초)
```
market_list       → 팩 목록. 출처 이력(어느 에이전트가 언제부터 언제까지, 몇 건) 보여줌
market_preview    → 무료 미리보기로 품질 확인
market_subscribe  → SUI 결제 → 구독권 발급 (온체인 트랜잭션이 눈앞에서 일어남)
```

### 4. 구독 후 — 핵심 장면 (45초)
같은 질문을 다시 던진다.

→ `market_recall` 이 이전 소유자의 기억을 꺼내오고, 에이전트가 이렇게 답한다:
> "그건 만료가 아닙니다. 키 서버는 인증서 생성 시각이 자기 시계보다 **1ms 라도 미래이면 거부**합니다(허용 오차 0). PC 시계가 2~3초 빠른 것만으로 재현됩니다. TTL 을 낮추거나 키 서버를 바꿔도 소용없습니다."

**심사위원(개발자)이 30초 안에 차이를 판별할 수 있는 장면.**

### 5. 회수 (30초)
구독 만료 후 다시 `market_recall` →
> "구독이 만료되었습니다."

Seal 이 온체인 정책(`seal_approve`)을 확인하고 복호화 키를 내주지 않는다.
**블록체인이 없으면 불가능한 장면.**

## 예비 질문 (심사위원이 물을 것)

| 질문 | 답 |
|---|---|
| README 나 문서 파는 거랑 뭐가 다른가 | 문서에는 "이 접근은 시도했다 실패했다"가 안 남는다. 기억은 실제 작업에서 자동으로 쌓이고, 에이전트가 검색해 바로 쓴다. 출처 이력이 온체인에 있어 진짜인지 검증된다. |
| MemWal 델리게이트로 공유하면 되지 않나 | 델리게이트는 계정 **전체**를 열고, 최대 20명, 결제·만료 개념이 없다. 컨트랙트상 소유자당 Seal 열쇠가 1개라 팩 단위 부분 공개가 구조적으로 불가능하다. |
| 구독자가 복호화한 뒤 재배포하면 | 막지 못한다. 다만 사본에는 출처 이력이 없어 정품과 구분된다. 향후 과제. |
| 만료 후에도 이미 받은 키로 읽히지 않나 | 그렇다. Seal 은 이미 발급된 키를 소급 회수하지 못한다. 회수는 **새 접근**에 즉시 적용된다. 그래서 MCP 서버는 요청마다 키를 새로 받는다. |
| 팔 기억이 있는 사람이 실제로 있나 | 코딩 에이전트를 매일 쓰는 개발자. 이 프로젝트 자체가 그 사례다. |
